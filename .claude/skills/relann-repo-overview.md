# RelaNN Repository Overview

RelaNN is a declarative framework for building neural networks over relational data, bringing SQL-like simplicity to neural network development. This doc gives a balanced summary of the repo for agent orientation; no single component is documented in full here.

## Repository Layout

- **`relann/`** — Main library (parser, term_graph, tensor_term_compiler, era_operations, relnn, engine, session, pydantic_classes, etc.). Each `.py` is a **juplit-paired notebook**: jupytext header at the top, cells delimited by `# %%` and `# %% [markdown]`, inline tests gated with `if test():`. The `.py` is the source of truth; the matching `.ipynb` is gitignored and generated by `uv run poe sync`.
- **`tests/`** — Standalone pytest files organised by bucket: `smoke/`, `feature/`, `dhn/`, `slow/`, `repro/`, `scaffold/`.
- **`examples/`** — User-facing demos (juplit `.py`).
- **`research/`** — Reproducibility artefacts (`paper_experiments/`, `_drafts/`).
- **`docs/`** — Design notes; **`docs/cursor-rules/`** holds the original `.cursor/rules/*.mdc` content migrated to plain markdown.
- **`.claude/skills/`** — Claude Code skills: `juplit-programming`, `write-relnn-program`.
- **`pyproject.toml`** — single source of truth for build (uv), poe tasks, juplit config, jupytext format, and pytest options.

## Core Components

1. **Parser** (`relann/parser.py`) — Parses DSL with Lark grammar into Pydantic classes (rules, transforms, fit/predict).
2. **Term Graph** (`relann/term_graph.py`) — Builds a NetworkX computational graph from rules: data loaders, join/union, selection, **transformation** (holds TensorTerm embedding expressions), aggregation.
3. **Tensor Term Compiler** (`relann/tensor_term_compiler.py`) — Compiles one TensorTerm (embedding expression) into one PyTorch `nn.Module`. Used by Engine during materialization; resolves ops from run scope → built-ins (ArgMax, Concat, Tensor) → torch.nn → torch.
4. **ERA Operations** (`relann/era_operations.py`) — Embedded Relational Algebra: Join, Aggregation, Transformation, DataLoader, etc.
5. **RelNN** (`relann/relnn.py`) — PyTorch executor: `instantiate()` (content/structure) and `forward()` (embeddings).
6. **Engine** (`relann/engine.py`) — Symbol tables, relations, term graphs, parameters; drives parsing, graph build, and compilation (e.g. `tensor_term_to_module` via TensorTermCompiler). Manages template specialization dispatch, recursion, and bounded-set expansion.
7. **Session** (`relann/session.py`) — High-level API (run DSL, fit, predict).

## Understanding the RelNN Language

### Rule Structure: LHS and RHS

Rules follow Prolog/Datalog-style syntax:
```
LHS(attributes; embedding_expression) :- RHS(attributes; embedding_vars) .
```

**Left-Hand Side (LHS):**
- Defines output relation name and schema
- Specifies embedding computation (neural network transformations)

**Right-Hand Side (RHS):**
- Lists input relations and how they're combined
- Specifies which embeddings to use from each input
- Defines relational operations via operators:
  - `,` (comma) = **Join** operation
  - `|` (pipe) = **Union** operation
- Can include filter conditions

**What the RHS Does:**

The RHS builds the computation graph:

1. **Input Relations**: Each relation becomes a node in the term graph
2. **Relational Operators**: 
   - `,` = Join (combines relations by matching attributes)
   - `|` = Union (concatenates rows)
3. **Join Key Inference**: Automatically infers join keys from shared attribute names
4. **Filter Conditions**: Optional comparisons after relations
5. **Embedding Variables**: The `; z` parts specify which embeddings to use

**Example:**
```relnn
MsgPassing1(target_id; sum(z * w)) :- PapersEmb1(citing; z), Citation(citing, target_id; w) .
```

This RHS:
- Takes `PapersEmb1` with embedding `z`
- Joins with `Citation` (join key: `citing`)
- `Citation` has embedding `w` (edge weights)
- Multiplies `z * w` and aggregates by `target_id` using `sum`

### How the Language is Built

**1. Grammar Definition** (`relann/relann_grammar.lark`):
- Uses Lark parser generator
- Defines syntax for rules, transforms, fit/predict statements, functions

**2. Parsing Pipeline** (`relann/parser.py`):
```
DSL String → Lark Parser → Parse Tree → RelnnTransformer → Pydantic Classes
```

**3. Term Graph Construction** (`relann/term_graph.py`):
```
Pydantic Rule → TermGraph.add_rule() → NetworkX DiGraph
```

For each rule, `add_rule()`:
1. Adds Data Loader nodes for RHS relations
2. Creates relational operator nodes (Join/Union) when multiple relations are combined
3. Adds Selection nodes if filter expressions exist
4. Creates Transformation nodes for neural network operations (each stores a **TensorTerm** — the embedding expression, e.g. `Linear(3,4)(z)`, `ReLU()(z)`)
5. Adds Aggregation nodes for grouping operations
6. Maps symbol names to output nodes

**4. Tensor Term Compilation** (`relann/tensor_term_compiler.py`): Engine compiles each transformation node’s TensorTerm into an `nn.Module` via `TensorTermCompiler(engine).compile(tterm, ...)`; result stored as `torch_transformation` on the node. Op names are resolved in order: DSL-native (`view`, `sqrt`, `transpose`) → run scope → built-ins (ArgMax, Concat, Tensor) → torch.nn → torch.

**5. Module Materialization** (`relann/relnn.py`, `relann/engine.py`):
```
Term Graph → Engine.eval_tensor_terms_on_tg() (compile each TensorTerm) → RelNN Module → PyTorch nn.Module
```

### What the Language Does (Execution Semantics)

**Execution Flow:**

1. **Parse**: DSL string → Pydantic `Program` object
2. **Graph Building**: Each rule adds nodes/edges to term graph
3. **Materialization**: On `fit`/`predict`, Engine compiles transformation nodes to modules and RelNN builds the executable PyTorch module

**Two-Phase Execution:**

**Phase 1: `instantiate(data)` - Content Pass**
- Performs relational operations (joins, unions, filters)
- Computes data structure (DataFrame content)
- Caches join keys and grouping information
- Sets up computation graph structure

**Phase 2: `forward(data)` - Embedding Pass**
- Uses pre-computed structure from `instantiate()`
- Applies neural network transformations to embeddings
- Propagates embeddings through the graph
- Returns final output embeddings

**Why Two Phases?**
- Efficiency: Join operations are expensive but don't change between forward passes
- Caching: Relational structure can be cached and reused
- Separation: Content (structure) vs. Embeddings (neural network values)

### Example

```relnn
# Constants
in_channels = 1433 .
hidden_channels = 16 .
out_channels = 7 .

# Layer 1: Embedding transformation
PapersEmb1(pid; Linear(in_channels, hidden_channels, False)(z)) :- Papers(pid; z) .

# Layer 1: Message passing - join, multiply, aggregate
PapersAgg1(target_id; sum(z * w)) :- PapersEmb1(citing; z), Citation(citing, target_id; w) .

# Layer 1: ReLU
PapersAggNL1(target_id; ReLU(z)) :- PapersAgg1(target_id; z) .

# Layer 2: Second embedding
PapersEmb2(target_id; Linear(hidden_channels, out_channels, False)(z)) :- PapersAggNL1(target_id; z) .

# Layer 2: Message passing
PapersAgg2(target_id; sum(z * w)) :- PapersEmb2(citing; z), Citation(citing, target_id; w) .

# Training
?fit <epochs=200, lr=0.01, weight_decay=0.0005> Loss(; CrossEntropyLoss()(z_pred, z)) :- PapersAgg2(target_id; z_pred), Labels(target_id; z) .

# Prediction
?pred Output(target_id; z) :- PapersAgg2(target_id; z) .
```

**Key Syntax:**
- Rules: `LHS(attrs; embedding_expr) :- RHS(attrs; embedding_var) .`
- Embeddings separated by `;` from content attributes
- Module calls: `Linear(3, 4)(z_in)`
- Aggregations: `sum(z * w)`
- Fit: `?fit <params> Loss(...) :- ...`
- Predict: `?pred Output(...) :- ...`

### Templates, Specialization, and Bounding

The DSL supports C++-style template specialization and compile-time bounded-set expansion, enabling fully generic architectures like HGT:

- **Template specialization**: Multiple definitions of the same template name (e.g. `H<'Author', 0>` base case + `H<type, layer>` general case). The engine dispatches to the most-specific match based on concrete vs wildcard parameters.
- **Recursive templates**: A function `H<type, L>` can reference `H<type, L-1>` in its body; base cases terminate the recursion.
- **Bounded sets**: `Union(Set(ER<...> | GuardRel(...)))` iterates over a DB relation at compile time, expanding the template once per matching row. `Join(Set(ER<i>(...) | 1 <= i, i <= h))` iterates over an integer range.
- **Splat**: `Concat(*z)` inside a `Join(Set(...))` auto-expands to `Concat(z_1, z_2, ...)` matching the number of expanded ERs.
- **Weight sharing**: Globally-defined templated rules (base cases) are materialized once in the global term graph, ensuring shared weights even when referenced from nested functions.
